**Gate amendment: applied 2026-10-14 (spec e3dd66f).** Memory is `phys_footprint`, summed over every process of each app including its `sshgate hub`, both apps unlocked with one tab open, idle; thresholds unchanged. The first footprint run (0776fa4, superseded below) showed the hub holding about 72 MiB after the Argon2id derive in both apps, which sent the gate to STOP; the hub was then changed (1281bd2, cb199b5, 798acd7: `argon2Key` calls `debug.FreeOSMemory()` after each derive and, on darwin, caps GOMAXPROCS) and the gate re-measured here.

**The KDF release is empirical, with a miss rate of about 5%.** The hub change returns the 64 MiB work area to the OS after each derive and is measured by its authors as about 95% effective: about 1 unlock in 20 keeps about 72 MiB until the next unlock. In the 4 unlocked runs here (2 per app, plus one extra mygo launch that never got past the lock screen and is not counted) the hub was released every time (Electron hub 7.8-8.5 MiB, mygo hub 7.6-10.1 MiB), so no extra run was taken; that is 4 of 4, which fits a 5% miss rate but does not measure it. What a miss costs in the gate's terms, from the 3 min medians (Electron 151.3 MiB with an 8.2 MiB hub, mygo app 35.75 MiB + 8.9 MiB hub), with the hub at about 72 MiB: mygo's hub misses, Electron's does not: 35.75 + 72 = 107.8 MiB, 71% of Electron, the 40% half FAILs and the 120 MiB ceiling still passes. Both hubs miss: mygo 107.8 against Electron 151.3 - 8.2 + 72 = 215.1 MiB, 50.1%, FAIL. Only Electron's hub misses: 44.7 / 215.1 = 20.8%, PASS. The 40% half holds while mygo's hub stays below 24.8 MiB (0.4 × 151.3 - 35.75). So a given unlock of the mygo app has about a 5% chance of a hub that, measured on that run, would fail this gate; the gate value here is the median over the runs taken, as the amended spec defines it.

## Findings to carry into slice 1

- The memory gate passes only because the hub releases its Argon2id work area after each derive (1281bd2, cb199b5, 798acd7; empirical, about 5% of unlocks keep about 72 MiB until the next one). Before that change the hub was 70.7-72.4 MiB footprint unlocked in both apps (superseded subsection). Slice 1 should either make the release deterministic or accept the 5% case; a miss in mygo's hub puts the 40% half at 71%.
- The hub and the app both keep their post-flood memory (207 MiB and 104 MiB RSS), with no release at idle.
- The terminal view draws a hollow cursor while the window is not key, and keystrokes sent before the tab exists are lost (expected, noted only because GUI driving hit it).
- The sshtestd shell is an echo shell with no line feed after Enter, so `echo hi` shows as an overwritten first line; it proves the echo path, not command execution.
- GUI driving: cmux-cua's background type/key delivery worked once the field had been pixel-clicked; the end of a flood cannot be seen through its tools, hence the sampler.
- The slice-0 app ignores `locked`: after the hub idle-locks, the open tab still accepts input (the hub accepts `term.write` while locked). The slice-0 binary is for measurement only, not daily use. Slice 1 must cover tabs on `locked`.
- Hub failure is now shown on the unlock screen (`App.HubState`: the supervisor's `failed` message with the last stderr lines, `hub restarting (attempt N)`), but an already open tab is not touched when the hub dies or restarts, and a restarted hub starts locked; slice 1 owns that with the lock handling.
- The throughput spec's other assertions (keystrokes during a flood, frame gap ≤ 200 ms, memory stability) are not ported; slice 0 measures only the flood rate.
- Hub KDF residue: addressed by the release above; not released after a flood either (hub 207 MiB RSS after the floods, bullet above), which is a separate matter.
