**Decision: STOP, as the gate is written.**

Failing gate: memory, the ≤ 40% of Electron half (mygo 108.8 MiB against Electron 217.2 MiB is 50.1% at 3 min; the 120 MiB ceiling passes). Bundle PASS, flood PASS and libghostty build PASS do not offset it, and the pending human checks below can only add failures, not remove this one.

**Gate amendment: applied 2026-10-14 (spec e3dd66f).** Memory is `phys_footprint`, summed over every process of each app including its `sshgate hub`, both apps unlocked with one tab open, idle; thresholds unchanged. The amendment assumed that `ps` RSS overstated the hub by about 70 MiB after the Argon2id KDF because Go returns pages with `MADV_FREE_REUSABLE`. The footprint re-measure does not bear that out: the hub's footprint is 70.7-72.1 MiB unlocked (RSS 77.4-78.2 MiB), so the KDF memory is dirty memory, not reusable pages, in both apps (Electron's hub: 71.8-72.4 MiB). The amendment fixed the metric, not the hub; the hub is 66% of mygo's total and 33% of Electron's.

A hub-side fix (for example `debug.FreeOSMemory()` after unlock, untested) changes `internal/hub`, which the spec lists as Out of scope, so it needs a spec ruling of its own. Indicative only, not a re-grade: with the hub at its locked size (about 11.5 MiB), mygo would be about 37 + 11.5 = 48 MiB, and Electron about 217 - 61 = 156 MiB, so 31%; the hub would then have to be fixed for both apps.

## How each number was taken

**Bundle.** `go build -trimpath -ldflags="-s -w"` for `app/build/sshgate-app` (13,060,610 B) and `app/build/sshgate` (8,758,002 B), plus `app/build/natives/libghostty-vt.dylib` (2,257,696 B) and the installed `sshgate-touchid` (123,856 B). Sum 24.2002 MB.

**Idle memory (footprint).** Both apps are this repo's builds at e3dd66f, unpackaged, each against its own sshtestd vault (server `box`, password `pw`), its own `SSHGATE_STORE` and a short `SSHGATE_RUNTIME_DIR`, run one at a time on a quiet machine. Same state for both: one unlock with the right password, one terminal tab open, nothing typed, idle. Electron: a throwaway Playwright spec (deleted, not committed) using `launch()`, `unlock()` and `openBox()` (tab `data-state="open"`, one tab, `.xterm` visible; screenshots kept in the notes); mygo: the app from `app/build/sshgate-app` with the repo-root `sshgate` as hub, unlocked through the GUI (cmux-cua), the open terminal view checked on a screenshot at the start and at the end of each run. **Flood, mygo.** `flood 209715200` typed into the tab through the GUI. The key tool cannot report the end of the flood, so a background sampler ran next to it: `netstat -ib -I lo0` byte counter every ~15 ms (the flood crosses loopback hub to sshtestd) and `screencapture -l <window>` every ~130 ms with an MD5 of each capture. Onset is the first sample with more than 400 KB moved; the flood ends on screen at the first capture that equals the final steady state (FLOOD-DONE drawn, cursor blink only). Time from onset to that capture was 1.12, 1.13, 1.12 s, so 187, 186, 186 MB/s (median 186). Wire time alone was 0.99-1.01 s (208-211 MB/s). Resolution of the screen end is about 0.13 s (about 10%; even at -10%, about 167 MB/s or 350% of Electron, the flood still passes), and the start is the first byte on the wire, not the key event, a few ms later at most. The sampler scripts were not kept. This is a different method than Electron's spec (which times from its own send to the last byte acked into xterm), so the ratio is indicative; with a 4x margin the verdict does not depend on it. A sanity check: lo0 moved 213 MB per run.

## Human checks still to do (not counted as passed)

The automated halves pass headless with the source-built library, in app/view/term_test.go: IME commit sent once as the user (`TestHubIMECommitIsOneUserWrite`, `TestIMECommitSentOnceAsUser`), typed key `user:true` and query reply `user:false` (`TestHubTypedKeyIsUserAndQueryReplyIsNot`), paste text `user:true` (`TestHubPasteIsUserWrite`, `TestCopyAndPaste`), copy sends nothing (`TestHubCopySendsNothing`), and Ctrl+C/V/D/W/R reach the shell with the terminal staying open (`TestHubControlKeysReachTheShell`), plus OSC 52 and the menu check above. These are ports of desktop/e2e/ime.spec.ts and clipboard.spec.ts, except that the Electron clipboard spec's Ctrl+Shift+C/V binding is the Windows/Linux one; on macOS the paste and copy ports use the editor's `paste` and `copy` commands. What remains is real input only:

1. Telex through the OS input method: with Vietnamese Telex, type `tieesng` in the tab and confirm `tiếng` appears once at the remote prompt. (The remote here is the sshtestd echo shell, so it echoes what the terminal sends.)
2. A real selection with Cmd+C and Cmd+V: select text in the tab, press Cmd+C then Cmd+V, and confirm it pastes. Optionally rerun `printf '\e]52;c;aGVsbG8=\a'` on a real remote and confirm the clipboard does not change.
3. VoiceOver: turn it on (Cmd+F5), focus the master password field, and confirm it is announced as a secure text field and the typed characters are not read aloud. The accessibility tree lists the field as `AXTextField (Master password)` and shows no secure subrole, so check by ear that it is announced as secure and the characters are not read.

## Findings to carry into slice 1

- The memory gate fails on the 40%-of-Electron half, and the hub is the biggest part of it: footprint 70.7-72.1 MiB unlocked in mygo (11.5 MiB RSS locked), 71.8-72.4 MiB in the Electron app, the same code. mygo's app process is 36.6-37.9 MiB footprint. If the hub returned its KDF memory (for example `debug.FreeOSMemory()` after unlock, untested) both apps would drop by about 60 MiB: mygo to about 48 MiB, Electron to about 156 MiB, 31%. A repeated unlock attempt grows the hub further (136 MiB after two key derivations) and it is not released in 3 minutes.
- The hub and the app both keep their post-flood memory (207 MiB and 104 MiB RSS), with no release at idle.
- The terminal view draws a hollow cursor while the window is not key, and keystrokes sent before the tab exists are lost (expected, noted only because GUI driving hit it).
- The sshtestd shell is an echo shell with no line feed after Enter, so `echo hi` shows as an overwritten first line; it proves the echo path, not command execution.
- GUI driving: cmux-cua's background type/key delivery worked once the field had been pixel-clicked; the end of a flood cannot be seen through its tools, hence the sampler.
- The slice-0 app ignores `locked`: after the hub idle-locks, the open tab still accepts input (the hub accepts `term.write` while locked). The slice-0 binary is for measurement only, not daily use. Slice 1 must cover tabs on `locked`.
- Hub failure is now shown on the unlock screen (`App.HubState`: the supervisor's `failed` message with the last stderr lines, `hub restarting (attempt N)`), but an already open tab is not touched when the hub dies or restarts, and a restarted hub starts locked; slice 1 owns that with the lock handling.
- The throughput spec's other assertions (keystrokes during a flood, frame gap ≤ 200 ms, memory stability) are not ported; slice 0 measures only the flood rate.
- Hub KDF residue (about 60 MiB footprint after unlock, 67 MiB RSS, not released in 5 minutes idle) is most of the memory gap; a fix is in `internal/hub` and needs a spec ruling first.
