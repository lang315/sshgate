**Decision: STOP, as the gate is written.** The spec says to stop the project and stay on Electron if any gate fails, and the idle RSS gate fails: 164.3 MiB against the ≤ 120 MiB ceiling (this FAIL stands on its own; the ≤ 40% half was not measured against its baseline). Bundle PASS, flood PASS and libghostty build PASS do not offset it, and the pending human checks below can only add failures, not remove this one.

**Proposed gate amendment, for the owner to decide (not applied, and the verdict above does not use it).** The re-measure below shows the overage is the hub's, not the UI's: the same `sshgate hub` that the Electron app runs holds about 78 MiB once unlocked (11.5 MiB locked), which matches Argon2id's 64 MiB working memory (`MemoryKiB` 65536, `internal/config/crypto.go:39`), and it does not shrink in 5 minutes of idle. mygo's own app process is 85.9-90.1 MiB. The owner could amend the gate to count the app process only, or to the app plus a locked-size hub (about 97 MiB, inside 120 MiB), or to compare unlocked mygo against unlocked Electron. Any of these changes what the gate measures, so it is the owner's call, with the Electron baseline still to be measured. A hub-side fix (for example `debug.FreeOSMemory()` after unlock) changes `internal/hub`, which the spec lists as Out of scope, so it needs a spec ruling of its own.

## How each number was taken

**Bundle.** `go build -trimpath -ldflags="-s -w"` for `app/build/sshgate-app` (13,060,610 B) and `app/build/sshgate` (8,758,002 B), plus `app/build/natives/libghostty-vt.dylib` (2,257,696 B) and the installed `sshgate-touchid` (123,856 B). Sum 24.2002 MB.

**Idle RSS (mygo).** sshtestd vault (server `box`, password `pw`), app started from `app/build` with the repo-root `sshgate` as hub. Unlocked with `pw` through the GUI (cmux-cua), tab opened, `echo hi` typed (the sshtestd shell is an echo shell, so `echo hi` echoes; it runs nothing), 30 s idle, then `ps`. RSS figures in this report are MiB (`ps` KB / 1024); bundle sizes and flood rates are decimal MB (bytes / 10^6). Two fresh runs: A 86.3 + 77.9 = 164.2 MB (ps KB 88320 + 79776 = 168096) and B 85.9 + 78.4 = 164.3 MB (ps KB 88000 + 80256 = 168256). Before unlock the same pair is 75.7 + 11.5 = 87.2 MB. So the hub gains about 67 MB at unlock and keeps it (RSS, not heap in use; most likely the Argon2id working memory that Go has not returned to the OS). After the floods the hub reached 207 MB and the app 104 MB and did not shrink while I watched.

**Idle RSS re-measure (disclosed extra evidence; it does not re-grade the gate).** Why: the hub's +67 MiB at unlock matches Argon2id's 64 MiB, and the 30 s sample could precede Go's forced GC (2 min on an idle process). Reading: the hub does not give the memory back across the 2-minute forced GC; it rises from 77.6 to 78.2 MiB. The total grows 162-163 to 165-168 MiB over 5 minutes (the app grows, 84.5-85.2 to 87.2-90.1 MiB). So the 30 s reading was not an artefact of GC timing. What this does not show: heap in use against RSS inside the hub (not measured), and whether `debug.FreeOSMemory()` would return it (not tried). Tab liveness: in run 1 the window was not frontmost and the keystrokes did not reach the tab (nothing echoed); in run 2 the window was brought to the front and the first key `e` echoed, so the tab took input, but the rest of `echo hi` did not arrive (the cmux-cua tool lost focus). The sampled RSS is therefore of an unlocked app with one open, idle tab, but without the earlier `echo hi` having been typed. Two earlier launches in this session (a wrong password, a typing check) were stopped before sampling and are not used.

**Idle RSS (Electron).** Per the controller ruling the installed app was not touched. Measured as it is running now with the brief's awk: 5 processes (main 83.7, GPU 43.3, network 24.8, renderer 67.3, hub 17.7) = 236.7 MB at the first reading, 244.3 MB later. The state of that app (locked or unlocked, tabs open) is unknown; a 17.7 MB hub suggests it was locked, and the like-for-like note below assumes so. Spike figure from earlier today: 335 MB. The 335 MB figure comes from the spec's spike table (2026-10-14, installed app, its 18 MB hub included), so it is not an unlocked reading either. Both are shown because the gate verdict does not depend on which is used: 164 MB fails the 120 MB ceiling outright. Like for like, assuming the 244 MB reading was locked: locked against locked, mygo 87.2 MB against 244 MB is 36%; unlocked against unlocked, mygo 164.3 MB against an estimated Electron of about 244 + 67 = about 311 MB (its hub growing as mygo's did, 11.5 to 78.4 MB, by analogy, not measured) is about 53%, FAIL. The gate is defined as one tab, unlocked, so it stays FAIL, and the 120 MB ceiling fails outright in any case.

**Flood, mygo.** `flood 209715200` typed into the tab through the GUI. The key tool cannot report the end of the flood, so a background sampler ran next to it: `netstat -ib -I lo0` byte counter every ~15 ms (the flood crosses loopback hub to sshtestd) and `screencapture -l <window>` every ~130 ms with an MD5 of each capture. Onset is the first sample with more than 400 KB moved; the flood ends on screen at the first capture that equals the final steady state (FLOOD-DONE drawn, cursor blink only). Time from onset to that capture was 1.12, 1.13, 1.12 s, so 187, 186, 186 MB/s (median 186). Wire time alone was 0.99-1.01 s (208-211 MB/s). Resolution of the screen end is about 0.13 s (about 10%; even at -10%, about 167 MB/s or 350% of Electron, the flood still passes), and the start is the first byte on the wire, not the key event, a few ms later at most. The sampler scripts were not kept. This is a different method than Electron's spec (which times from its own send to the last byte acked into xterm), so the ratio is indicative; with a 4x margin the verdict does not depend on it. A sanity check: lo0 moved 213 MB per run.

**Flood, Electron.** `(cd desktop && npm run build && npx playwright test e2e/throughput.spec.ts)` passed: `mbPerS` 47.38, `elapsedS` 4.43, `maxFrameGapMs` 19, memory peaks main 174 MB, renderer 210 MB.

**OSC 52.** In the tab, ESC, `]52;c;aGVsbG8=` and Ctrl+G were sent as keys; the sshtestd shell echoes input, so the terminal parsed `ESC ] 52 ; c ; aGVsbG8= BEL`. Nothing was drawn (the sequence was consumed as an OSC) and `ZZ` typed after it showed normally. `pbpaste` before and after: identical (sha f367bcc93c7b, 60 bytes), also identical after the later floods. The clipboard did not change.

## Human checks still to do (not counted as passed)

The automated halves pass headless with the source-built library, in app/view/term_test.go: IME commit sent once as the user (`TestHubIMECommitIsOneUserWrite`, `TestIMECommitSentOnceAsUser`), typed key `user:true` and query reply `user:false` (`TestHubTypedKeyIsUserAndQueryReplyIsNot`), paste text `user:true` (`TestHubPasteIsUserWrite`, `TestCopyAndPaste`), copy sends nothing (`TestHubCopySendsNothing`), and Ctrl+C/V/D/W/R reach the shell with the terminal staying open (`TestHubControlKeysReachTheShell`), plus OSC 52 and the menu check above. These are ports of desktop/e2e/ime.spec.ts and clipboard.spec.ts, except that the Electron clipboard spec's Ctrl+Shift+C/V binding is the Windows/Linux one; on macOS the paste and copy ports use the editor's `paste` and `copy` commands. What remains is real input only:

1. Telex through the OS input method: with Vietnamese Telex, type `tieesng` in the tab and confirm `tiếng` appears once at the remote prompt. (The remote here is the sshtestd echo shell, so it echoes what the terminal sends.)
2. A real selection with Cmd+C and Cmd+V: select text in the tab, press Cmd+C then Cmd+V, and confirm it pastes. Optionally rerun `printf '\e]52;c;aGVsbG8=\a'` on a real remote and confirm the clipboard does not change.
3. VoiceOver: turn it on (Cmd+F5), focus the master password field, and confirm it is announced as a secure text field and the typed characters are not read aloud. The accessibility tree lists the field as `AXTextField (Master password)` and shows no secure subrole, so check by ear that it is announced as secure and the characters are not read.

## Findings to carry into slice 1

- Idle RSS fails because of the hub, not the UI: hub 11.5 MB locked, 78.4 MB after unlock. App alone is 85.9 MB (the spike's terminal probe read 78 MB idle). If the hub returned its KDF memory (for example `debug.FreeOSMemory()` after unlock) the total would be about 97 MB (85.9 + 11.5), which is inside the 120 MB ceiling, but this is untested. The hub is the same code in the Electron app, so the Electron figure would also grow after an unlock.
- The hub and the app both keep their post-flood memory (207 MB and 104 MB), with no release at idle.
- The terminal view draws a hollow cursor while the window is not key, and keystrokes sent before the tab exists are lost (expected, noted only because GUI driving hit it).
- The sshtestd shell is an echo shell with no line feed after Enter, so `echo hi` shows as an overwritten first line; it proves the echo path, not command execution.
- GUI driving: cmux-cua's background type/key delivery worked once the field had been pixel-clicked; the end of a flood cannot be seen through its tools, hence the sampler.
- The slice-0 app ignores `locked`: after the hub idle-locks, the open tab still accepts input (the hub accepts `term.write` while locked). The slice-0 binary is for measurement only, not daily use. Slice 1 must cover tabs on `locked`.
- Hub failure is now shown on the unlock screen (`App.HubState`: the supervisor's `failed` message with the last stderr lines, `hub restarting (attempt N)`), but an already open tab is not touched when the hub dies or restarts, and a restarted hub starts locked; slice 1 owns that with the lock handling.
- The throughput spec's other assertions (keystrokes during a flood, frame gap ≤ 200 ms, memory stability) are not ported; slice 0 measures only the flood rate.
- Hub KDF residue (about 67 MiB after unlock, not released in 5 minutes idle) is the cause of the idle RSS FAIL; a fix is in `internal/hub` and needs a spec ruling first.
