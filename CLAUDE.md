# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

`sshgate`: a single Go binary, three modes. `sshgate --host=...` is a standalone MCP stdio server exposing `exec`, `sudo-exec`, and `list-servers` over one CLI-configured connection; it never touches the on-disk vault. Without `--host`, `sshgate` is a stateless bridge that forwards those same three tools over stdio to `sshgate hub`, a separate process that owns the vault, the SSH connections, and an approval `broker` that blocks every AI-issued command on a human decision by default, unless the AI-issued command's host has an auto-allow grant (plain exec by default, or sudo-exec and root hosts with a per-host opt-in); the native mygo app in `app/` is the UI-door client, on macOS only (installed in `/Applications`); the Electron app in `desktop/` was removed in November 2026 (plan `2026-11-02-retire-electron.md`), so Windows and Linux have no desktop app; `sshgate hub --cli` is a terminal stand-in for the same role, for headless use. The browser config UI (`sshgate web`) is gone; `sshgate web` now only fails with a pointer to the app. The project was ported from TypeScript; the TS code is gone (`9a10b56`).

If Docker is unavailable, integration tests skip themselves instead of failing. They start `lscr.io/linuxserver/openssh-server` and connect with `Insecure: true`. `cmd/sshgate/e2e_test.go` is the exception: it drives a real bridge → hub → sshd approval flow but fakes the SSH server in-process (`internal/sshx/sshtest`), so it has no `testing.Short()` guard and needs no Docker.

## Architecture

`cmd/sshgate/main.go` routes on the first argument: `hub` goes to `runHub` (`hub.go`), `web` fails with a removal message, `version`/`--version` prints `sshgate <mcpserver.Version>` ("dev" unless set with `-ldflags -X`; it is also the version both MCP servers report), and anything else starts `runMCP` — standalone with `--host`, or a bridge to the hub without it. The hub reads the store at `~/.config/sshgate/servers.json`.

**Hub and bridge** (`internal/hub`, `internal/broker`, `internal/rpc`, `internal/mcpserver/bridge.go`):
- `sshgate hub` owns the unlocked vault, the `sshx.Registry`, and the approval `broker`. `ServeUIDoor` serves a full-privilege JSON-RPC "UI door" on stdio (`hello`, `status`, `unlock`, `lock` (`{stopAuto?}`), `servers`, `pending`, `decide`, `denyAll`, `vault.create`, `servers.save`, `servers.delete`, `servers.forgetHostKey`, `servers.setAutoAllow`, `servers.autoAllowCheck`, `import.scan`, `import.apply`, `term.*`, `files.list`, `files.mkdir`, `files.rename`, `files.plan`, `files.run`, `files.cancel`, `files.cancelAll`, `tunnels.list`, `tunnels.save`, `tunnels.delete`, `tunnels.start`, `tunnels.stop` (a notification), `audit.read`, `settings.setSoftLockLimit` (`{limit}`: `24h`, `3d`, `7d`, `none`; strict params; needs an unlocked vault; writes `config.File.SoftLockLimit` under the MAC and a `softLockLimit` config record); the hub also pushes `audit.appended` for every audit record while unlocked; protocol 12, `ProtocolVersion` in `idle.go`; `status` reports `autoHosts` (the hosts with a live grant) only under soft lock; the `locked` notification's params are `{reason}` only (the app tells a soft lock from a hard one by `status.autoHosts`), and the door sends it only while the generation it carries (`h.lockGen`, bumped at every lock-state change) is still the hub's current one, so a note for a state the hub has left is dropped; `unlock` replies `ranWhileLocked: [{server, count}]` when auto runs finished while the UI was locked; `decide` refuses `allowed` and `sent_to_tab` with `ErrLocked` while locked, soft or hard, and still takes `denied`), consumed by the `app/` desktop app; `hub --cli` instead runs `RunCLIApprover`, a separate plain-text terminal protocol over the same `Hub`, not JSON-RPC. `ServeMCPDoor` serves a restricted "MCP door" on a per-user Unix socket / named pipe (`SocketPath`: `$SSHGATE_RUNTIME_DIR/sshgate`, else `/run/user/<uid>/sshgate` if owned by us, else `/tmp/sshgate-<uid>`; never `TMPDIR`/`XDG_RUNTIME_DIR`, and tests isolate via `SSHGATE_RUNTIME_DIR`), peer-checked both directions (UID on Unix, SID on Windows): only `listServers` (`{name, host, locked}` per AI-visible server; the bridge prints `- name (host)`), `exec`/`execStdin`/`sudoExec` (request-only, so a long approval wait can't stall the read loop; stdin travels only on `execStdin`, which the bridge uses when `stdin` is non-empty, so a hub that predates it answers "method not found" — the bridge tells the AI to restart the app — instead of running the command without its stdin, and `exec`/`sudoExec` refuse a `stdin` param) and `cancel` (a notification, so it can't get stuck behind one) are registered — nothing there can unlock, decide, or read secrets.
- Without `--host`, `sshgate` is a stateless bridge (`BuildBridgeServer`): MCP stdio in, one fresh MCP-door connection per tool call. It validates nothing and holds no secrets; the hub is the single policy point. `server` has no default here — empty fails the same as an unknown name.
- `Hub.Unlock` copies the KDF under `h.mu`, derives the key (Argon2, about 1 s) without it, then checks verifier and MAC under it again, refusing the key when the KDF changed meanwhile (`the vault changed during unlock; try again`). An AI exec that arrives mid-derive sees a locked vault, so a test must wait for the unlock to end before an AI exec.
- Every MCP exec goes through `broker.Submit` and blocks for a human decision (cap 5 pending, 5-minute expiry), unless its host has an auto-allow grant (see Auto-allow below); under soft lock a request that cannot run under a grant fails at once, unaudited, and never reaches the broker. `OnEvent` runs synchronously on the caller's goroutine with the broker's lock released, and `Decide` blocks until the matching "pending" event has gone out — a handler that calls `Decide` from inside its own "pending" callback deadlocks. No other auto-approval rules exist; do not add any without a spec change.
- Audit log: `sshgate hub` appends one JSON record per line to `audit.jsonl` next to the store (`~/.config/sshgate/audit.jsonl`). Exec records carry `outcome`, `waitMs` (time spent waiting for a decision) and `approval: "auto"` for auto-allowed runs; config records carry `kind: "config"` and `action` (`save`, `autoAllowOn` with `until`/`forever`, `autoAllowOff` with `reason`, …). It is the ground truth for "did this run need a click", not what a person remembers.
- `Hub.Exec` order: the first resolve is `resolveForAuto`, under the grant rule (under soft lock a server with a live grant resolves; a failure of this resolve for a server that has a grant, in any lock state — hidden, removed, unpinned, or the resolve itself failing, but not `ErrLocked` — ends that grant with reason "server changed", and the AI sees the same error): vault exists (else `ErrNoVault`, audited) → visible → unlocked → host key pinned → sanitize command, validate description (control/format runes rejected, 500-byte description cap, no `--maxChars` equivalent; the description is metadata for the approver and audit and is never appended to the command) → validate stdin (`config.ValidateStdin`: `\n`, `\t`, `\r`, ZWNJ, ZWJ and BOM allowed (`forbiddenRuneExcept`), other control and Cf runes, over 256 KiB (`MaxStdin`), and `[REDACTED:` refused), then refuse stdin with sudo (`config.ErrStdinSudo`) or on a su-password host (`config.ErrStdinSu`), unaudited and before `autoStart` and the broker → auto-allow: a plain exec (or, with the host's `AutoAllowSudo` opt-in, a sudo exec) on a host with a live grant runs on the resolved connection with no approval (see Auto-allow; `autoStart`, which also returns an `autoSkip`: `skipNone`, `skipBusy`, `skipSudo`) → if `autoStart` returns no run and the hub is locked (`h.Locked()`, checked after it, so it also covers the run that just ended the last grant), `ErrAutoBusy` (`maxAutoInflight` runs in flight), `ErrNeedsApproval` (a sudo exec without the opt-in, which `autoStart` checks before the in-flight cap), or `ErrLocked`, returned with no audit record (a retrying client would otherwise append one per retry) and never reaching the broker → otherwise `broker.Submit` blocks for approval (the request's `target` is the `user@host:port` shown to the approver) → re-check ctx and re-verify the server with `resolveForAI` (strict rule: `ErrLocked` under soft lock even on a granted host; state can change during the wait); `user@host:port` and the pin must still match the approved ones, else `ErrServerChanged` ("server changed") → run with a per-request timeout (a stdin exec runs through `Executor.ExecStdin` → `sshx.Manager.ExecStdin`, which also refuses `SuPassword` with `sshx.ErrStdinUnsupported` (a su password saved during the wait; `forAI` turns it into `ErrStdinSu`) and feeds stdin through `StdinPipe` after `Start`, so a command that exits 0 without reading all of it is not an error; the approver sees the stdin as `broker.Request.Stdin`, `AuditRecord.Stdin` is `red.Redact(stdin)` (vault secrets masked; capped at 4096 on the no-vault path), `autoAllow.ran` carries only `stdinBytes`, and `decide` with `sent_to_tab` is refused for it, `broker.ErrSendToTabStdin`, as is the CLI approver's `s`) → redact and cap each stream in one step (`config.RedactCapStreams`: vault secrets with `config.Redactor` (a value masked as `***` counts as kind `secret`, via `Redactor.RedactCount`/`config.RedactCap`), then `config.RedactPatterns`, then the cap; the cap keeps head and tail, and only those windows, each widened by 64 KiB and aligned to line boundaries (the cut fragment is dropped only when shorter than 64 KiB, so a long-line output keeps max/2 per half; aligned output can be shorter than the cap, and a line of 64 KiB or more that masking shrinks by 32 KiB or more within itself can keep a cut piece), are pattern-masked, so cost stays bounded, while masking a window before cutting keeps a PEM block cut by the cap from leaving an unmatched piece; a lone `-----END … PRIVATE KEY-----` is masked from the start only in a tail window whose head the cap cut off, and every cut moves inward off a `[REDACTED:…]` marker or a multibyte rune, so output can be a few bytes shorter than the cap) → audit every branch, including denied/expired/cancelled; an allowed run's record carries `redacted`, the per-kind mask counts, never a value. Hidden and nonexistent servers return byte-identical errors. SSH and resolve failures reach the AI only as generic text (`ErrHostKeyFailed`, `ErrConnFailed`; timeouts, `sshx.ErrTimeout`, pass through redacted); the detail goes to the audit reason and stderr. The bridge lays the already-processed result out as `exit code:`/`stdout:`/`stderr:` (`layoutExec`) without reprocessing it; `ExecResponse.Redacted` (JSON `redacted`, omitted when empty) becomes one final `note: sshgate redacted N values (kind ×n, …); the values are withheld from AI clients` line, kinds in `config.RedactKinds` order. There is no bypass: to see a real value the human uses Send to tab.
- Auto-allow (`autoallow.go`): `servers.setAutoAllow {server, mode}` (`off`, `15m`, `30m`, `60m`, `2h`, `4h`, `forever`) arms or ends a per-host grant, held in `h.mu` (`grants map[string]*grant`, `until` zero for forever, a `snap` of the server's `target`/`hostKey`/`hostKeyAlgo`/`auth` taken when enabled); it refuses a hidden, nonexistent, locked or no-vault, unpinned host, and — unless the server's `AutoAllowRoot` opt-in is set — a `root`-login or su/sudo-password host. `sudoExec` on a granted host runs auto only when the server's `AutoAllowSudo` opt-in is set (audited with `approval: "auto"` and `sudo: true`); otherwise it always waits for approval. Both opt-ins default to false, are independent, and are written only by `servers.save` (`ServerInput.autoAllowRoot`/`autoAllowSudo`, copied by `ApplyServer`, ignored by `dialChanged`, cleared by `vault.create`). `servers.save {original, server, autoAllow}` (protocol 7) arms a grant for the given mode in the same `h.mu` section as the write, after ending any old grant; if arming fails the save still stands and the call returns an error prefixed `saved, but auto-allow was not turned on: `. A plain exec (or, with the opt-in, a sudo exec) on a granted host is checked against `snap` and the opt-ins on the current server (any mismatch ends the grant, "server changed") and against a cap of 2 in-flight auto runs per host (a 3rd goes to approval); it never increments `h.running` and never counts as UI activity, so back-to-back auto runs can't hold the vault unlocked forever. No grant delays the idle lock, and the Lock button is no stop: with a live grant both soft-lock (`Hub.LockKeepAuto`, the UI door's `lock {}`, locked reason `manual`; `LockKeepAuto` first sweeps expired grants (reason "expired"), then in one `h.mu` section soft-locks with a live grant or hard-locks with none; the door's `lock` accepts `stopAuto` only as `true`/`false` and answers anything else (extra keys, a non-boolean, `null`) with a hard lock first, then -32602; `lock {stopAuto: true}` is `Hub.Lock`, a hard lock that ends every grant with reason "locked"; `softlock.go`: `enterSoftLocked` moves the key out of `deps.MasterKey` into `h.autoKey`, so `lockedLocked()` — the vault has a KDF and `deps.MasterKey == nil` — is true with no soft-lock case, and so are `writeKeyLocked` (which tests `deps.MasterKey` itself) and `serversForUI` (via `Deps.IsLocked`): every reader of the key is strict by default), and without one they hard-lock. Only two functions read the key's bytes from `autoKey`: `resolveAutoLocked` (callers `resolveForAuto`, `autoStart`, `grantStaleLocked`) and `vaultKeyLocked` (caller `reloadLocked`, so the vault file's MAC is still verified under soft lock); other code only tests `autoKey != nil` as the soft-lock state (`lockIfIdle`, `sweepGrants`, `hardenLocked`, `lockStatus`, `aiLockedLocked`, `autoExec`, `zeroKeyLocked`). "Soft-locked" is `autoKey != nil`; invariant under `h.mu`: `autoKey != nil` implies `deps.MasterKey == nil` and at least one live grant; every removal from `h.grants` (`endGrantLocked`) runs `hardenLocked`, so the key never outlives the last grant (zeroed, `locked` with reason `grantsEnded`). Two more tests of `autoKey != nil` refuse or hide something from a locked UI: `autoAllowOff` refuses under soft lock, and `autoStateLocked` hides live grants from a locked UI. `checkGrantLocked` (`aiLockedLocked`: the key is absent, or under soft lock the server has no grant or the soft lock has reached the vault's soft-lock limit (`pastLimitLocked`)) has exactly two callers, `resolveForAuto` and `autoStart`; every other path, `resolveForAI` included, stays on `checkLocked`, which treats soft lock as locked (`lockedLocked()`). `sweepGrants` under soft lock reloads the vault (a failed reload ends every grant, which hard-locks) and runs the per-grant stale check (`grantStaleLocked`, reason "server changed") only when the vault file differs from the one the grants were last checked against (`h.sweptFile`, nil on entering soft lock so the first sweep checks every grant once), not on every tick. `autoExec` decides in one `h.mu` section: a run that succeeded under soft lock is counted in `h.ranLocked` (returned and cleared by `unlock`, `TakeRanLocked`); while unlocked it sends `autoAllow.ran`; a failed run under soft lock, or a run finishing under a hard lock, is neither counted nor sent. The vault's soft-lock limit (`config.File.SoftLockLimit`: absent = 24 h, the default `maxSoftLock`; `3d`, `7d`, `none`; an unknown value reads as 24 h; wall clock), read live from `deps.File` by `pastLimitLocked` at its two checks (`aiLockedLocked`, `lockIfIdle`) and never copied into hub state, hard-locks and ends every grant with reason "soft lock limit" (`locked` reason `softLockLimit`). `status.softLockLimit` reports it only while unlocked; `vault.create` clears it. Under soft lock `reloadLocked` refuses a copy with a lower `Revision` than the one in use (a replayed older copy), for every caller; the sweep then sees a failed reload, every grant ends and the hub hard-locks. `servers.setAutoAllow` is refused with `ErrLocked` in every mode under soft lock (`off` included: `lock {stopAuto: true}` is the one stop), as are `servers.save` and the other writers (`writeKeyLocked`). A forever grant needs Resume only after a hard lock or a restart. Every `servers.save`, `servers.delete`, `servers.forgetHostKey`, and `vault.create` turns a grant off (and clears the forever flag); a reload never arms one, only `servers.setAutoAllow` and `servers.save` do. `servers.autoAllowCheck {server}` runs `id -u; sudo -n true 2>/dev/null && echo nopasswd` on the pinned connection for the Auto-allow dialog's root warning; it is advice, not a gate. Every auto exec is audited like an approved one but with `approval: "auto"`; config actions are `autoAllowOn`, `autoAllowResume`, `autoAllowOff`, `autoAllowCheck`. The MCP door has no auto-allow method and `listServers` does not show it, except that under soft lock `ServersForMCP` reports a host with a live grant as not locked.
- Host writes (`hosts.go`): `vault.create` derives the key once and saves, reloads, and unlocks in one `h.mu` section (kept servers lose `aiVisible` and their host-key pins; a KDF-less file with `Enc*` fields is refused; it is refused while the file or the hub's in-memory copy has a KDF, so a vault whose file went missing is not replaced). `servers.save`/`delete`/`forgetHostKey` need an unlocked vault (`writeKey`/`writeKeyLocked`: `ErrLocked` or "create a vault first") and hold `h.mu` across their own `config.Update`, the `Reload` that follows, and ending the server's auto-allow grant, so they serialize with `servers.setAutoAllow` and any grant still armed when that section runs provably predates the write and is ended unconditionally (a rename ends it under both the old and new name); a failed post-write reload is returned to the caller (the write itself stands). The hub remembers the last reload error (a vault file that went missing counts as one: the hub keeps the last good copy and writes still fail, since `config.Update` will not sign a KDF-less file; a missing file when there never was a vault is just "no vault"), and `status` reports it as `storeError`, a fixed message with nothing from the file, which the app shows as a red banner until a reload succeeds. A save closes the server's connection (`Registry.Close`) only when the stored server changed beyond `aiVisible` (`dialChanged`), and denies its pending AI requests ("server changed"). Each writes a `kind: "config"` audit record (`broker.ConfigRecord`), never a secret.
- Import (`import.go`, `internal/sshconfig`): `import.scan` lists every alias in `~/.ssh/config` (`Options.SSHConfigPath`, `hub --sshConfig`; `Include` followed, patterns dropped) and resolves each with `ssh -G` (found with `exec.LookPath`, 5 s timeout, never dials): the first `IdentityFile` holding a private key gives key auth (agent auth instead when the key is encrypted and the ssh-agent holds it, as ssh would sign with that copy), else agent; `ProxyJump`/`ProxyCommand` hosts are skipped; the pin comes only from your user known_hosts files (`UserKnownHostsFile`, normally `~/.ssh/known_hosts`; `sshx.KnownHostKey`: ed25519, then ecdsa, then rsa; never a revoked or `@cert-authority` key). `import.apply {aliases}` takes names only, recomputes every field, and adds the ready ones as new servers (`aiVisible` false, no secrets) in one `config.Update`, with one `import` config audit record each. Both need an unlocked vault.
- Files (`files.go`, `filejobs.go`, `internal/files`): `files.list/mkdir/rename` run on the manager's shared SFTP client (`Manager.SFTP`, its setup bounded by `sftpSetupTimeout`, 30 s); `pinnedClient` refuses an unpinned server before touching the registry. Transfers and deletes are jobs (`files.plan` answers at once — a plan for an id still in use is refused — and walks in the background, `files.planned` is sent under the job lock so `files.done` always follows it, then `files.run {conflict}` → `files.progress`… → `files.done`; `files.cancel` is a notification and works while locked; `files.cancelAll` is main-only; a job stuck planning or running is force-closed after `cancelGrace`, 2 s, by closing its whole SSH channel — `sessionCloser`, since closing only stdin waits on the server), each on its own SFTP channel (`Manager.NewSFTP`). Params are decoded strictly (`strictParams`: exact keys, no duplicates). Remote names are untrusted (one element, UTF-8, `filepath.Localize` for downloads, case clashes are errors); local I/O goes through `os.Root` and local errors never carry absolute paths (`bare()`); files are written to random `O_EXCL` part files (a download's created 0600 locally; an upload's only inside a folder that is already 0700: a folder the run made itself, else a staging folder `.<name>.<random>.sshgate-part/` beside the destination, since `pkg/sftp` has no create-with-mode and a chmod cannot revoke an fd another user opened in between; `makePrivate` keeps an inherited setgid bit, which Linux's chmod would clear, and refuses a folder swapped for a link; a server that refuses `Mkdir` gets the part file beside the destination, chmodded 0600 one round trip after creation, as before), and committed without replacing unless the author chose overwrite; walks never follow symlinks (a selected one is resolved once) and an upload source swapped for a symlink after the plan is refused (`Lstat` + `SameFile`); a folder whose mkdir failed gets none of its files; depth limit 64 levels inclusive; duplicate top-level upload names are rejected; delete never uses `RemoveAll`. `servers.save/delete/forgetHostKey` end a server's jobs (`"server changed"`) before closing its connection. Each job writes start and end `kind: "file"` audit records (local paths included); mkdir and rename write one.
- Tunnels (`tunnels.go`, `internal/tunnel`): local, remote, and dynamic (SOCKS5) forwards are saved per server in the vault (`config.Tunnel`), written only by `tunnels.save`/`tunnels.delete` through `config.Update`, and kept by `ApplyServer` across other edits; `dialChanged` ignores them (and `aiVisible`), so saving a tunnel or flipping visibility never closes the connection. `tunnels.start` runs the forward on the manager's shared client (`Registry.Get`/`mgr.Client()`) and binds loopback only — the bind address is not a field — needs an unlocked vault and a pinned host key, and never prompts to trust one. Running tunnels are the hub's, not any door's, so they survive lock; `tunnels.stop` is a notification and works while locked. `tunnels.delete` of a running tunnel ends it first. A tunnel ends on `client.Wait` ("connection lost") or on a server change (`endServerTunnels`, "server changed"); start and end each write a `kind: "tunnel"` audit record. No MCP-door access.
- Audit (`audit.go`, `internal/broker/audit.go`): `broker.Audit` counts lines at open with a streaming count (a record's `seq` is its 1-based line number; a torn last line is ended there), tracks the file's byte size, and recounts under its lock before an append when the file's size is not the tracked one (a hand edit, a truncation, a second hub), so the live `seq` stays the line number `Read` reports; it calls `OnAppend` after each write with its lock released. `audit.read {before?, limit?, server?, kinds?, outcomes?, text?}` (strict params; limit 0 means 200, over 500 or negative is -32602; `ErrLocked` while locked; counts as UI activity) reads the file backwards from its end, newest first, in 64 KiB chunks (`linesBackward`), and stops at the first older match past the limit, so the file is never held in memory and the newest page costs one chunk however large the file is; it reads only the bytes below the size recorded under the lock (after a recount there when the file's size is not the tracked one, since `seq` is counted down from the tracked line count) and releases the lock before the read, so a slow read never holds up a writer (`ponytail:` a page deep in the file still walks down from EOF to `before` without parsing, and a search with few matches still scans to the start; a byte offset with `next`, and rotation, when that shows) and returns `{records: [{seq, record}], next?, skipped, path}`; only lines that start with `{` and parse are returned, the rest count in `skipped`, which covers only the span that call scanned (down to the last record returned, or to the start of the file when nothing older matches), so the app adds up the pages of one list. `kinds` and `outcomes` are a union (kind in `kinds`, or an exec record whose outcome is in `outcomes`: `auto` is `approval: "auto"`, `allowed` excludes it, `cancelled` is `approved_but_cancelled` or `cancelled_running`); `server` (exact; a record also matches when its `servers` contains it, which is how a `softLock` record is found by host) and `text` (case-insensitive substring of the record's decoded string and number values, joined with newlines; never key names or JSON escapes) narrow it. A `kind: "file"` record's `local` paths are stripped inside `broker.Audit` (`Read`, before matching, and the `OnAppend` line; the file on disk keeps them), so file records' `local` paths never reach the app and a `text` search cannot find them. The footer shows the audit file's own path (`path`). `audit.appended {seq, record}` goes out for every record while unlocked, through a 256-slot queue with one drain goroutine per UI door; the sink never blocks, and a record is dropped when the reader is 256 behind (the drain checks `h.unlocked` and notifies under a door-local mutex that the `locked` notification also takes, so nothing is sent while the hub is locked; a record still queued across a lock and an unlock may go out after the unlock) (the app dedupes by seq and has Refresh). The callback can run with `h.mu` held (`CreateVault`, `SaveServer`, `SetAutoAllow`, grant ends), so it reads only atomics: `h.unlocked`, which means exactly `deps.MasterKey != nil`, set wherever `deps.MasterKey` changes (`Unlock`, `CreateVault`, `enterSoftLocked`, `zeroKeyLocked`, and the test helper `unlockForTest`), and `h.auditSink`. `autoAllow.ran` is sent under `sendMu`, like `audit.appended`, and only while `h.unlocked` is true (`autoExec` also sends it only when it found `deps.MasterKey` set), so a locked UI gets neither (`autoAllow.off`, a server name only, is still sent). Entering soft lock writes one `kind: "config"` record, action `softLock`, with `servers`, the hosts whose grants are live, and `reason` (`manual` or `idle`). The test helpers `startUI`/`startUIRaw` drop `audit.appended`; `startTermDoor` keeps it. No MCP-door access.

**mcpserver.Deps holds one connection source at a time** (`internal/mcpserver/resolve.go`):
- Standalone `--host` mode: `buildDeps` builds `Deps.CLI` from `config.ParseArgv`'s `--key=value` flags (`--host`, `--user`, `--password`, `--key`, `--sudoPassword`, `--suPassword`, ...) as the `"(default)"` server; it never reads the on-disk store (`Deps.File` stays nil).
- `sshgate hub` builds `Deps.File` from the on-disk store and never sets `Deps.CLI`; there's no `"(default)"` server through the hub.
- `Deps.Resolve(name)` still has both branches (shared code) and turns either source into a `sshx.DialConfig`, decrypting secrets on demand. The file branch serves only the hub: `StrictHostKey`, the stored `HostKeyAlgo`, and no learner. Without a master key, encrypted servers are "locked" and fail with a clear error. Key/agent-only servers still resolve there, but the hub refuses every AI exec, and every UI-door `term.open`, while the vault is locked (hard-locked; under soft lock, hosts with a live grant run auto) — its MAC is unchecked until unlock — and `listServers` then reports every server locked (under soft lock, `ServersForMCP` reports a host with a live grant not locked). Under soft lock the key is not in `deps.MasterKey` but in `h.autoKey`, so `Deps.IsLocked` is true for every encrypted server; `resolveAutoLocked` resolves on a copy of the deps that carries it. A store with no KDF (no file, or a KDF-less one) is "no vault" to the hub (`noVaultLocked`): it was never MAC'd, so `listServers` is empty, AI exec fails with `ErrNoVault` (audited, never dialled), and `term.open` fails with "create a vault first"; `vault.create` is the only way forward.

**Store crypto** (`internal/config/crypto.go`, `store.go`):
- Argon2id derives the master key, and the KDF params plus a verifier blob are stored in the file; the KDF returns its 64 MiB work area to the OS after each derive (`debug.FreeOSMemory`; on darwin `GOMAXPROCS` is lowered to the KDF parallelism around the derive and release, empirical with the mechanism unknown, serialized by a mutex).
- Each secret field uses AES-GCM with an HKDF subkey labelled `"<serverName>/<field>"`. Its AAD binds version, name, field, host, port, user, and auth (`AADFor`). Renaming a server or changing host/port/user/auth therefore invalidates its ciphertexts. `config.ApplyServer` (the hub's `servers.save`; `ServerInput` secrets are write-only: nil keeps, "" clears) re-encrypts a kept secret only when its AAD changes, and on a host or port change drops the pin and every secret not re-supplied.
- A whole-file HMAC (`MAC`) is checked on load when a master key is present. `Save` bumps `Revision`, recomputes the MAC, and writes atomically (temp file, then rename, mode 0600).
- `config.Update(path, masterKey, fn)` is the only store writer (hub, `RecordHostKey`): a package mutex plus `withFlock` (unix; mutex only elsewhere), then load (a missing file starts empty), check key and MAC for a KDF store (refused without a key), run `fn`, save. Nothing is written when `fn` fails, or when a key is given but the file has no KDF after `fn` (a vault stripped of its KDF is never re-signed; the hub's reload likewise refuses a file that lost its KDF).
- A corrupt or unreadable store is a hard error in both modes and is never overwritten.
- The master key is never read from an environment variable or file (`SSHGATE_MASTER_PASSWORD_FILE` is gone): `sshgate hub` gets it only from an explicit `unlock` call (the UI door's `unlock` method, or the CLI approver's `u` command). `--host` mode never touches the vault at all.

**SSH layer** (`internal/sshx`):
- `Registry` caches one `Manager` per server name, keyed by a hash of the `DialConfig` (secrets, `HostKey` and `HostKeyAlgo` included, callbacks excluded). A changed config closes the old connection and dials fresh. The comparison uses the manager's current pin, so a manager that just learned a key by TOFU is kept when the caller comes back with that same pin or with no pin (`--host` mode only: a strict caller's empty pin is never filled from the cache). `Registry.Close(name)` closes and drops one manager; its terminals see EOF and send `term.exit`.
- `Manager` holds one lazily dialed `ssh.Client` behind a mutex. When `SuPassword` is set, plain `Exec` runs inside a persistent `su` root shell, framing each command with a random nonce marker (`FrameSuCommand`). A wrong su password must fail closed, never falling back to an unprivileged shell. `ExecSudo` wraps commands with `sudo -S` or `sudo -n` (`wrap.go`).
- Host keys (`hostkey.go`): every hub path dials strict (`DialConfig.StrictHostKey`): no pin fails with `*HostKeyUnknownError`, a different key with `*HostKeyMismatchError` (wraps `ErrHostKeyMismatch`); both carry the presented key. Nothing on a hub path learns a key, and the approval path refuses an AI-visible server with no pin (`ErrNoHostKey`). The UI door's `term.open` answers those as results (`{status: "hostKeyUnknown", fingerprint, keyType, knownHosts, ...}`, `{status: "hostKeyMismatch", pinned, presented, ...}`), never errors. A retry with `trustHostKey: {fingerprint, keyType}` dials pinned to exactly that key and records it with `config.RecordHostKey`, which writes only while the server is unpinned and still has the dialled host and port (`ErrPinSkipped` otherwise, and the open fails); a failed reload after the write does not fail the open, it only sets `storeError`). `knownHosts` (`KnownHostsHint` on `~/.ssh/known_hosts`, `Options.KnownHostsPath` in tests) is a hint for the human, never pinned. A pin's `HostKeyAlgo` limits `HostKeyAlgorithms` to its family. TOFU (`OnLearnHostKey`, the `Manager` keeping a learned pin) remains only in `--host` mode. `--insecureIgnoreHostKey` skips checks and warns on stderr; it is `--host` mode only, and `sshgate hub` refuses to start with it.

**MCP tools** (`internal/mcpserver/tools.go`): the `--host`-mode tool set. `runExec` validates the command (`SanitizeCommand` rejects control characters and enforces `--maxChars`; `exec` takes `stdin` (`ExecInput.Stdin`), checked with `config.ValidateStdin` and refused on a su-password host, while `sudo-exec` (`SudoInput`) does not), appends the description as a shell comment, resolves the server, and runs it. Output and errors pass through `config.Redactor`, which masks every secret in the `DialConfig`; output then goes through `config.RedactPatterns` and the cap together (`FormatExec` → `config.RedactCapStreams`) and ends with the same `note:` line as the bridge. Keep that redaction on every path that returns text.

**`app/`** (the mygo desktop app, its own Go module; spec `2026-10-14-mygo-desktop-design.md`, built in slices 0 to 7; wraps the hub's UI door, protocol 12; ported from the removed Electron app, so comments naming `desktop/src/...` files point into git history):
- Packages: `hubproc` (spawns `sshgate hub` as `hubLaunch` does, restarts it with backoff), `door` (the JSON-RPC client), `hubapi` (typed calls and notifications), `model` (pure rules ported from the Electron renderer's TypeScript modules, with their tests), `view` (the `App` controller and screens on mygo's `ui`), `termconn` (terminals over `term.*` for the libghostty-vt plugin), `touchid`, and `cmd/sshgate-app` (window, tray, menu, hub launch, background mode).
- Idle lock: every UI-door request except `status` counts as UI activity (`internal/hub/idle.go`, `uidoor.go`), as does a `term.write` with `user: true`, which the app sets only within `termconn.UserWindow` (1 s) of a real key, paste or input-method commit. So the app never polls `servers` or `pending` (or anything but `status`) and never calls the hub in response to `autoAllow.ran`, `autoAllow.off` or a timer: any of those would keep the vault unlocked forever.
- Packaged (`mygo.App.IsPackaged()`: the bundle path ends in `.app`) the app ignores and strips every `SSHGATE_*` knob and loads only the `libghostty-vt.dylib` in Resources whose SHA-256 is the one embedded at build time. It uses `~/Library/Application Support/sshgate` (`touchid.json`, in the format the Electron app wrote, so Touch ID carried over; `theme.json`) and the hub's socket and vault.
- Touch ID (`touchid`, `view/touch.go`, spec `2026-10-12-touchid-unlock-design.md`; helper source `app/native/touchid/main.swift`): `touchid.Manager` runs `sshgate-touchid` (`available`, `enroll`, `unlock`; exit 2 cancelled, 3 key gone, 4 not usable) and keeps `touchid.json`; the password goes helper → manager → the hub's `unlock` and never into a view. Settings' Unlock section (macOS only) turns it on with the master password typed again; Save applies Touch ID first, then the limit if it changed, and a Touch ID error leaves the limit unsaved. The unlock screen has an **Unlock with Touch ID** button and asks by itself once per locked episode (`model.AutoTouch`: at start with the window focused, or on the first focus while locked; never at the moment of locking). A typed unlock that succeeds, or a hub that stops, cancels a dialog still up. Tests use `touchid/testdata/fake-touchid.sh`; the real helper is a hand check.
- mygo pin: `app/go.mod` replaces `github.com/egoist/mygo` with the fork `github.com/lang315/mygo` at a pseudo-version (`go mod edit -replace github.com/egoist/mygo=github.com/lang315/mygo@<commit>`, then check API changes). `view/term.go` must keep `NoClipboardWrite: true`: the fork lets OSC 52 set the local clipboard otherwise (`TestHubNoClipboardWrite`).
- View tests: folds (`Collapsible`) and audit row details animate, so what they show has no size until `tt.Advance`; use `clickFold` (`view/editor_test.go`) and `tt.Advance`, never a wall-clock wait (the Tester's clock does not follow it). `./view` takes about 6 minutes under `-race`.
- Background mode (`cmd/sshgate-app/background.go`, macOS only): a window close hides the window and the Dock icon (`Dock.Hide`), `OnBeforeQuit` sets `quitting` so Cmd+Q, the tray's Quit and SIGTERM still close it, and the tray's Show, a notification click and `OnActivate` call `showWindow` (`Dock.Show`, restore, show, focus). The hub and the unlocked vault keep running until the idle lock.


## Conventions

- Security posture is intentional (fail closed, generic errors, redaction, no secret persistence outside the encrypted store). Recent commits (`fix: refuse corrupt config store...`, TOFU host keys) show the expected bar. Add a test when you change any of these paths.
- One exception to "no secret persistence outside the encrypted store": `touchid.json` holds the master password sealed to this Mac's Secure Enclave, behind Touch ID, opt-in (spec `2026-10-12-touchid-unlock-design.md`, Security). The app reads and writes it in `app/touchid`. Changing the master password, if a flow is ever added, must delete it.
- Design spec and implementation plan for the Go port are in `docs/superpowers/specs/` and `docs/superpowers/plans/`.
